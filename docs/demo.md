# The hosted demo

A public, read-only demo of the webapp on a generated mailbox. Every visitor
goes through the whole flow: the import screen, an import with its progress
animation, then the full app (graph, domains, message groups, rankings,
statistics, calendar). Contact edits are disabled.

## How it works

- **The data** is in [`demo/`](../demo/README.md): a generated mailbox and
  calendar, with made-up people on reserved domains. Nothing in it is real.
- **The server** (`DEMO_MODE=1`) imports `demo/` with the real parsers when it
  starts, before it listens, and records the import's progress. It serves that
  one database to everyone. Edits and imports answer `403`.
- **Each visitor's import** happens in their browser. Starting it plays the
  recorded progress back over about 8 seconds (`GET /api/demo/replay`); what
  they imported, with which name and whether with the calendar, is kept in
  their `localStorage`. Visitors never affect each other, and the server keeps
  no state per visitor. **Reset demo** in the banner forgets it.

Demo mode also:

- ignores `HF_API_KEY`, so the import is deterministic and offline;
- sets `FILL_EVENTS_NOW=2026-10-01`, so the calendar gives the same 105
  meetings whatever the date (see [`demo/README.md`](../demo/README.md));
- keeps its database in the system temp directory (`gmail-contact-graph-demo`),
  ignoring `DATA_DIR` and `CONTACTS_DB_FILE`, so it never imports over your own
  database.

## Run it locally

With Docker, on <http://localhost:5099>:

```bash
docker compose --profile demo up --build demo
```

The `demo` service has no `data/` volume and does not read `.env`. Do not set
`DEMO_MODE` on the `webapp` service instead: that one is for your own mailbox.

Without Docker, with the parsers and the webapp built (`make setup` in
`gmail-contact-graph/`):

```bash
cd gmail-contact-graph/webapp
DEMO_MODE=1 PORT=5099 npm run start
```

## Deploy on Railway

The demo deploys from `main` with [`railway.json`](../railway.json): Railway
builds `docker/webapp.Dockerfile` and waits for `/api/import/status`, which
answers only once the boot import is done. A failed import stops the server,
so Railway keeps the previous deploy.

Setting it up, once:

1. Create a Railway project: **Deploy from GitHub repo**, this repository,
   branch `main`.
2. Set the service variables: `DEMO_MODE=1` and `HOST=0.0.0.0`. Railway sets
   `PORT` itself. No volume.
3. **Settings → Networking → Generate Domain** for a public URL.
4. Check the first build log. If it fails on the `RUN --mount=type=cache`
   lines, remove the cache mounts from `docker/webapp.Dockerfile`: they only
   speed up local rebuilds.

Every merge into `main` deploys again.

## Changing the data

The files in `demo/` are generated by a script kept outside the repository,
and the demo, CI and the numbers in [`demo/README.md`](../demo/README.md) all
expect them as they are. If they change, update `FILL_EVENTS_NOW` in
`config.ts` to the day after the new calendar ends.
